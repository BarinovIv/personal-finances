# Обновление PWA при ручном перезапуске

Статус: ответы Q1–Q5 согласованы, реализация выполнена. Production-сборка, typecheck, полный набор тестов (461 тест в 42 файлах) и проверка границ модулей прошли. Жизненный цикл обновления проверен в Chrome через Playwriter. Независимые code-review по Standards и Spec завершены без замечаний.

## Решения пользователя

После релиза пользователь сам закрывает и снова открывает приложение. Рабочий экран сразу открывается из сохранённой оболочки; запуск не ждёт проверки релиза или скачивания обновления. При новом запуске приложение проверяет обновление и скачивает новую оболочку в фоне. Скачанная версия ждёт окончания текущей сессии, затем применяется при следующем открытии.

Перезапуск означает полную выгрузку PWA из списка открытых приложений и последующее открытие. Сворачивание и возвращение продолжают текущую работу. Проверок по таймеру, при возвращении из фона или восстановлении сети приложение не добавляет; текущий экран автоматически не перезагружается.

## Подтверждённое текущее поведение

- `packages/web/src/main.tsx` регистрирует service worker после загрузки страницы. Явных проверок при возвращении в приложение и обработчика смены worker для перезагрузки нет.
- `packages/web/src/sw.ts` скачивает оболочку, вызывает `skipWaiting()`, удаляет прежние кэши и вызывает `clients.claim()`. Это меняет worker, но не заменяет уже выполняющийся JavaScript экрана.
- На момент проверки 2026-10-05 production `/sw.js` и `/` отвечают с `Cache-Control: no-cache`.
- Сохранённые операции и очередь синхронизации записываются в IndexedDB одной транзакцией. Несохранённый ввод остаётся в памяти экрана.
- Версия оболочки в `packages/web/vite.config.ts` учитывает содержимое сборки, но не содержимое файлов из `public`. Замена иконки или manifest под прежним именем может не изменить service worker.

## Реализация

- Сохранить немедленное открытие приложения и регистрацию worker в фоне; явно выполнить проверку обновления при запуске, обработав отсутствие сети и ошибки.
- Убрать безусловные `skipWaiting()` и `clients.claim()`: использовать обычный режим ожидания worker до закрытия обслуживаемых им окон.
- Сохранить текущий кэш до активации новой версии. Ошибка скачивания новой оболочки не должна мешать запуску прежней.
- Включить содержимое файлов `public` в версию оболочки, чтобы изменение иконок и manifest также обновляло кэш.
- Не очищать IndexedDB или очередь синхронизации при обновлении оболочки.

## Согласованные условия

Если релиз появился после проверки в текущей сессии, первый перезапуск может ещё открыть старую версию и скачать новую в фоне. Следующий перезапуск после завершённого скачивания откроет новую. Это следствие выбранного запуска без ожидания обновления.

Если на том же устройстве приложение открыто также в браузере, обычная активация новой версии ждёт закрытия всех окон, которые используют прежний worker. Форсировать обновление поверх другой открытой сессии не предлагается.

## Критерии проверки

- Рабочий экран открывается, не дожидаясь сети или установки нового worker.
- Скачанная новая оболочка не меняет экран текущей сессии; после закрытия всех окон и нового запуска открывается новая версия.
- Сворачивание и возвращение не запускают проверку или перезагрузку со стороны приложения.
- Без сети либо при незавершённой установке работает прежняя сохранённая оболочка; локальные операции и очередь синхронизации сохраняются.
- Изменение только содержимого файла в `public` меняет версию оболочки.

## Ограничения механизма

Приложение не должно полагаться на обработчик закрытия для скачивания обновления: браузер на телефоне может завершить процесс без такого события. Если ОС восстанавливает прежний документ, это продолжение сессии, а не новый запуск. PWA не может гарантированно определить жест выгрузки во всех браузерах.

Браузер может самостоятельно проверять worker по событиям его жизненного цикла. Политика приложения ограничивает свои проверки и применение обновления, но не отменяет проверки браузера.

У старых установок нет новой логики проверки; доставка первого исправления зависит от существующего механизма обновления браузера.

## Источники

- [Жизненный цикл service worker](https://web.dev/articles/service-worker-lifecycle): проверки, установка, активация и сохранение страниц с прежней версией кода.
- [ServiceWorkerRegistration.update()](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/update): явная проверка версии worker.
- [Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api): заморозка, восстановление страницы и ненадёжность событий закрытия на телефоне.

## Проверка реализации

- Регрессионный тест `packages/web/test/pwa-build.test.ts` выполняет production-сборки в отдельном временном каталоге: одинаковые входные файлы дают одинаковый worker, замена содержимого manifest под прежним именем меняет worker. До исправления тест падал, после исправления проходит.
- В Chrome через Playwriter проверены две версии production-оболочки на временном локальном адресе. У прежней реализации новый worker сразу забирал управление открытой страницей; после исправления он остаётся в состоянии ожидания, старый кэш и введённый текст сохраняются. Закрытие одной из двух вкладок не активирует обновление; после закрытия всех вкладок новый запуск получает новую оболочку и прежний кэш удаляется.
- При задержанном ответе `/sw.js` рабочий экран открывается до завершения регистрации worker. При отключённой сети новая сохранённая оболочка открывается из кэша. При недоступном файле новой сборки установка не завершает обновление, а предыдущая оболочка продолжает работать и открывается без сети после перезапуска.
- Проверка браузером использовала Chrome, не мобильную ОС. Полная выгрузка установленной PWA на конкретном телефоне отдельно не проверялась.
